# Backend Rules

Rules for everything that runs on the server: database, sign-in, permissions, mutations, exports, payments and licensing. Read all of it before touching `src/server`, `src/proxy.ts`, `src/lib/supabase` or `src/app/api`.

Product context (roles, pipeline, pages) lives in [CLAUDE.md](CLAUDE.md). UI rules live in [FRONTEND_RULES.md](FRONTEND_RULES.md).

Precedence when things conflict: the project owner's instructions > this document > the agent's own habits.

---

## 1. Stack (required)

| Concern | Use | Notes |
|---|---|---|
| Runtime | **Next.js 16 App Router**, same app as the frontend | Server Components, Server Actions, Route Handlers. No separate API server |
| Database | **Postgres on Supabase** | Free tier during development; Pro before go-live (daily backups) |
| ORM / migrations | **Drizzle ORM + drizzle-kit** | Schema in TS, `casing: "snake_case"`. Driver `postgres` (postgres.js) with `prepare: false` |
| Sign-in | **Supabase Auth, Google provider only** | Via `@supabase/ssr`. Session refresh in `src/proxy.ts` |
| Files | **Supabase Storage**, private buckets | Served through short-lived signed URLs |
| Validation | **zod** (v4) | Schemas in `src/lib/schemas`, shared with the forms |
| Excel export | **exceljs**, generated on the server | Same filters and scope as the list it exports |
| Scheduled jobs | **Vercel Cron** → Route Handler guarded by `CRON_SECRET` | |
| Payments (later) | Vietnamese QR gateway webhook (SePay / PayOS — to be chosen) | §8 |

Before using any API above, check the current docs (Context7, or the bundled Next.js docs in `node_modules/next/dist/docs/`). Next.js 16 renamed `middleware.ts` to **`proxy.ts`** and enables **Cache Components** by default. Read `node_modules/next/dist/docs/01-app/02-guides/authentication-with-cache-components.md` before writing anything that reads the session.

**Do not use:** Prisma, a second ORM, raw `pg`, NextAuth/Auth.js or other auth libraries, the Supabase JS client for table queries (`supabase.from(...)`), Firebase, tRPC, GraphQL.

## 2. Layout

```
src/
  proxy.ts                    # session refresh + optimistic redirect (no role logic)
  lib/
    supabase/{client,server,proxy}.ts   # auth + storage clients
    auth/permissions.ts       # roles, can(), homePathFor() — shared with the UI
    schemas/                  # zod schemas shared by forms and server
  server/                     # server-only code ("server-only" import at the top)
    env.ts                    # zod-validated secrets
    db/
      index.ts                # `db` (bypasses RLS — see §4)
      schema/*.ts             # tables, one file per domain
      migrations/             # generated by drizzle-kit, committed
      seed/                   # reference data only (sources, templates)
    auth/
      session.ts              # getCurrentUser(), requireUser(), requirePermission()
      scope.ts                # studentScope(user) row filters
    queries/<domain>.ts       # reads, e.g. listStudents(user, filter)
    actions/<domain>.ts       # "use server" mutations
    audit.ts, result.ts
  app/api/                    # Route Handlers: webhooks, cron, exports, add-in license check
```

- Pages and components **never** import `@/server/db`. They call `src/lib/api/*` (FRONTEND_RULES §7), which calls `src/server/queries/*` when `NEXT_PUBLIC_USE_MOCK` is not `true`.
- One domain per file: `students`, `templates`, `payments`, `licenses`, `reports`, `referrals`.

## 3. Database conventions

- Table names: plural `snake_case`. TS keys: camelCase (mapped by `casing`).
- Primary keys: `uuid` with `defaultRandom()`. Human IDs (`R21`) are separate unique columns.
- Every timestamp is `timestamp({ withTimezone: true })`. Business dates (monthly reports, "sign-up month") are computed in **`Asia/Ho_Chi_Minh`**.
- Money: `bigint` whole VND (`amountVnd`). No floats, no decimals.
- Emails are stored **lowercase**. Phones are stored as digits only (`0901234567`). Formatting is the UI's job.
- Status changes write a row to `student_status_events`. History is never overwritten.
- No hard deletes of students, payments or licenses from the app. Use status (`dropped`, `revoked`) instead.
- **Every table calls `.enableRLS()`** (§4).
- Schema change workflow: edit `schema/*.ts` → `pnpm db:generate --name <what>` → review the SQL → `pnpm db:migrate`. Never edit an applied migration, and never use `drizzle-kit push` against the shared database.

### Student codes

`students.code` = source code + sequence (`A15`, `R21`). Allocated in the same transaction as the insert, using `UPDATE ad_sources SET next_seq = next_seq + 1 … RETURNING`. Never use `max(seq) + 1`. See `submitLeadSignup` in `src/server/actions/leads.ts` for the reference pattern.

## 4. Authorization — the most important section

The client's two fears are **losing data** and **leaking data**. The second one lives here.

1. **The app connects as the database owner, so RLS does not apply to Drizzle queries.** RLS is enabled on every table **with no policies**. That blocks anyone using the public Supabase key to reach the tables through the REST API. It does **not** protect our own queries. Our protection is rules 2–5.
2. **Every Server Action, Route Handler and query starts by resolving the caller:** `requireUser()` / `requirePermission("…")` from `src/server/auth/session.ts`. Query functions take `user: SessionUser` as their first argument, and never read the session on their own.
3. **Every query that touches `students`, or joins to it, includes `studentScope(user)`.** This is what limits sale A to their own leads. A query without a scope is a bug, even if the page that calls it is admin-only.
4. **Admin-only data** (payments, licenses, ad sources, settings, audit log) is checked with `requirePermission`, because the caller's scope is not enough on its own.
5. **Never return more columns than the screen needs.** Use explicit `select({ … })`. Never send a whole `students` row to a `sale` screen if it carries fields they shouldn't see.
6. Permissions are declared **once** in `src/lib/auth/permissions.ts`. Add new ones there, then use them in both the UI (`can`) and the server (`requirePermission`).
7. `src/proxy.ts` only refreshes the session and redirects signed-out visitors. It is an optimistic check, not security.
8. **Never cache per-user data with a shared `use cache`.** The session is read at request time behind `<Suspense>`. `getCurrentUser` is deduplicated with React `cache()`.

### Sign-in flow

1. `/dang-nhap` → `signInWithOAuth({ provider: "google", redirectTo: <origin>/auth/callback?next=… })`.
2. `/auth/callback` → `exchangeCodeForSession(code)` → `getCurrentUser()`.
3. No `users` row (or no roles) → `/chua-kich-hoat` ("tài khoản chưa được kích hoạt" + Zalo button). Otherwise → `homePathFor(user)`, or the `next` path if it starts with `/`.
4. `users` rows are created **before** first sign-in: by an admin for staff, or by "activate student" for a lead (sets `students.userId`, adds role `student`). The first sign-in links `authUserId`.

### Mock mode

`NEXT_PUBLIC_USE_MOCK=true` makes `getCurrentUser()` read the `rvpy-mock-role` cookie (set by the dev-only role switcher), and makes `src/lib/api` return `src/mocks` data. Mock mode is ignored when `NODE_ENV=production`.

## 5. Server Actions and Route Handlers

- Actions live in `src/server/actions/<domain>.ts` with `"use server"` at the top. They return **`ActionResult<T>`** (`src/server/result.ts`). They never throw to the client for expected failures. Error strings are Vietnamese, ready for a toast.
- Order inside an action: **parse input with zod → `requirePermission` → load the target with `studentScope` (404 if not visible) → mutate in a `db.transaction` → `audit(tx, …)` → `revalidatePath`/`updateTag`**.
- Every mutation writes to `audit_log` in the same transaction (`src/server/audit.ts`).
- Use Route Handlers (`src/app/api/**/route.ts`) only for machine callers: payment webhooks, cron, the add-in license check, and file downloads (Excel). Everything a page does goes through Server Actions.
- Public endpoints (sign-up form, add-in license check, webhooks) assume hostile input: zod-validate it, cap string lengths, and keep error messages generic.

## 6. Message templates

- `message_templates.body` uses `{{placeholders}}`. The allowed keys are defined in one map in `src/server/queries/templates.ts`: `ten`, `ma_hoc_vien`, `so_dien_thoai`, `hoc_phi`, `zalo_nhom_1`, `zalo_nhom_2`, `link_gioi_thieu`, …
- Placeholders are filled on the server with data the caller is allowed to see. Unknown keys are left visible as `{{key}}` so staff notice them.
- The site **never sends** Zalo messages. It renders the text and the UI offers a copy button (CLAUDE.md §2).

## 7. Exports, backups and the Google Sheets transition

- **Excel export** (`/api/export/<list>`) re-runs the list query with the **same filters and the same `studentScope`**, then streams an `.xlsx` built with exceljs. File name: `rvpy-<list>-<yyyyMMdd>.xlsx`. Column headers are in Vietnamese.
- **Monthly report** export follows the same rule. A `sale` user's report contains only their sources.
- **Nightly backup:** Vercel Cron → `/api/cron/backup` → one workbook with every business table → private Storage bucket `backups/`, keeping 30 days. A copy to the owner's Google Drive can be added later.
- **Transition from Google Sheets:** a one-off import script (`scripts/import-sheet.ts`) reads `.xlsx`/`.csv` exports of the current sheets into `students`/`payments`. There is **no live two-way sync** in v1. The owner keeps exporting from the site until they trust it.
- Real exported sheets are **never committed**. Put them in a git-ignored `data/` folder.

---

## 8. Payments, licenses, referrals (designed now, built later)

- **Payments** are entered by an admin for now. Later a QR gateway webhook (`/api/webhooks/payments`) verifies the signature, then inserts with `externalRef` as the idempotency key (unique), then advances the student to `paid`.
- **Licenses** are keyed by Google email. The add-in calls `GET /api/license/check?email=…&product=…` with an add-in API key, and gets back `{ active, expiresAt }` only. A 15-day trial and paid renewal will be specified in a later section.
- **Referral tiers** (CLAUDE.md §7) are computed on the server from `students.referredById` + status. The frontend shows the result and never calculates tiers.

## 9. Secrets and data

- Secrets live in `.env.local` (git-ignored) and in Vercel project env. `.env.example` lists every variable with no values.
- `NEXT_PUBLIC_*` may contain only the Supabase URL, the **publishable** key and the mock flag. The secret key and `DATABASE_URL` are server-only and go through `src/server/env.ts`.
- Never commit real student data, the client's sheet links, or exported files. Seeds contain reference data only. Fake people live in `src/mocks`.
- Never log full student rows, phone numbers or emails. Log IDs.

## 11. Don't

- Query the database from a component, a page, or `src/lib/api` directly. Go through `src/server/queries`.
- Write a `students` query without `studentScope`.
- Trust `role`, `sourceId` or `studentId` sent from the client. Derive them from the session.
- Add RLS policies that grant `anon`/`authenticated` access to tables. All data access goes through the server.
- Use `drizzle-kit push`, edit applied migrations, or hard-delete business records.
- Send Zalo messages, emails or payments automatically without the owner's explicit sign-off on that feature.
