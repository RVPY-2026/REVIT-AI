# Zalo Bot connection test

The owner authorized the Zalo Bot workflow. A local connection test and the first opt-in/onboarding integration are implemented.

Store `ZALO_BOT_TOKEN` in `.env.local`, never in public variables. Run `pnpm zalo:check` to verify the token without sending anything. Run `pnpm zalo:test` and send the printed, randomly generated command to the bot in a private Zalo chat. It sends two test messages to that chat and exits. Optional `ZALO_BOT_TEST_PHOTO_URL` adds one image using a publicly accessible HTTPS image URL. The runner ignores unrelated messages, groups, bots and old messages; it expires after 15 minutes. Do not run multiple polling processes.

The public signup creates a random, one-use 30-minute code and stores only its SHA-256 hash. It also creates an independent 256-bit browser ownership token, stored as a hash in `lead_signup_sessions` and as a seven-day HttpOnly cookie. Phone deduplication never returns an existing profile's code to another browser. Retrying from the owner browser reuses the same profile; the success page validates ownership and the current code hash before displaying a code. Its **Lấy mã kết nối mới** action renews on that profile with a one-minute cooldown and never replaces a connected chat. Lost/expired ownership requires staff support; existing pre-migration cookies are not ownership proof.

On the success page, the learner copies the code and sends it in a private chat to Bot RVPY. The webhook checks Zalo's `X-Bot-Api-Secret-Token` header, binds that chat to the exact signup and queues the separate community, offer and preparation messages. A bearer code proves possession of the browser-issued code, not ownership of the phone or a verified Zalo identity. Already connected profiles display their connection status instead of a new code.

The staff **Xác nhận học thử** action queues the thank-you photo when the learner has linked the Bot and `ZALO_BOT_THANKS_IMAGE_URL` is configured. CRM enrollment remains successful if Zalo delivery fails. Outbound messages are kept in the database queue with event keys and retry delays; a failed message holds later messages to the same chat in order.

Before deploying, apply migrations through `0003_signup_protection`, set `ZALO_BOT_TOKEN`, `ZALO_BOT_WEBHOOK_SECRET`, `CRON_SECRET`, and `ZALO_BOT_THANKS_IMAGE_URL` in the server environment, and set `NEXT_PUBLIC_ZALO_BOT_URL` if the Bot has a share link. Configure signup protection as described in `docs/signup-protection.md`. Set `NEXT_PUBLIC_SITE_URL` to the public HTTPS site, deploy, then run `pnpm zalo:webhook:set` to register `/api/webhooks/zalo-bot`. If the URL is a protected Vercel Preview, enable Protection Bypass for Automation and set its generated `VERCEL_AUTOMATION_BYPASS_SECRET` in the local environment; the setup script adds it as the documented `x-vercel-protection-bypass` query parameter. Treat that URL as a credential because it can bypass Preview protection. Local polling is development-only and refuses to run once a webhook is set.

### Retry scheduling on Vercel Hobby (Free)

Vercel's daily cron remains a fallback. The primary scheduler is Supabase Cron (`pg_cron` + `pg_net`), so no Vercel plan upgrade is needed. Enable Supabase Cron, `pg_net` and Vault in the project's dashboard. After deploying the worker and setting its `CRON_SECRET`, configure `.env.local` with `DATABASE_URL_DIRECT`, the deployed production `NEXT_PUBLIC_SITE_URL`, and the same `CRON_SECRET`. Run `pnpm zalo:cron:setup` for a read-only readiness check, then `pnpm zalo:cron:setup --apply` to install/update the named job. This setup is separate from schema migrations and is not activated automatically by a build.

The job runs every minute and only invokes the authenticated worker when a due item is not blocked by an earlier unsent message. The URL and credential are read from named Vault secrets, not embedded in cron command text. An empty queue causes no HTTP call. The worker drains up to 100 items per call within a 40-second budget (leaving time for the 15-second transport timeout); subsequent ticks continue the backlog. Delivery is at-least-once: an ambiguous provider timeout or a process crash after sending can still cause a duplicate. CRM displays pending count, oldest pending time and failed count.

Inspect the named job in Supabase Cron, `net._http_response` HTTP status/error records and application worker logs after deployment. Cron execution success alone only means the HTTP request was enqueued, not that Zalo delivered the message. Keep cron run history bounded according to Supabase's documented maintenance guidance. Free-project pausing or exhausted hosting quotas can delay processing; the daily fallback cannot guarantee minute-level delivery.

The onboarding sequence sends the text/links provided by the owner and can interleave optional public HTTPS images. `ZALO_BOT_OFFER_IMAGE_URL` follows the 9-day trial offer, and `ZALO_BOT_REFERRAL_IMAGE_URL` follows it with the referral-reward poster. `ZALO_BOT_COMMUNITY_IMAGE_URL` and `ZALO_BOT_PREP_IMAGE_URL` remain optional. The thank-you image uses `ZALO_BOT_THANKS_IMAGE_URL` and is sent only after staff confirms the student starts trial. Failed deliveries appear on the student profile and staff can retry them.
